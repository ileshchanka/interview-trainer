# Interview Trainer — тренажёр для подготовки к собеседованию по JS / TS / Angular

## Context

Задача — подготовиться к собеседованию по JavaScript, TypeScript и Angular, и одновременно
получить проект, который сам этой подготовке служит и который не стыдно показать интервьюеру.

Отсюда двойное требование к приложению: оно должно быть **реально полезным тренажёром**
(иначе им не будешь пользоваться) и **содержательным с точки зрения архитектуры**
(иначе о нём нечего рассказать). Оба требования закрывает связка из двух режимов:

- **карточки с интервальным повторением (SM-2)** — теория, которую надо помнить наизусть;
- **кодовая песочница «что выведет этот код»** — каверзные вопросы про event loop, `this`,
  замыкания, приведение типов, дженерики TS, которые словами не проверишь.

Технически это даёт ровно те темы, что спрашивают на собеседовании по Angular: standalone-компоненты,
signals, lazy-роутинг, DI, Reactive Forms, Web Workers, IndexedDB, чистое ядро под юнит-тестами.

Решения, принятые до начала работы:
- стек — Angular (CLI 22.1.6, Node 24 уже стоят) + Angular Material + TypeScript strict;
- бэкенда нет, весь прогресс локальный (IndexedDB), деплой на GitHub Pages;
- оба режима делаются в одной итерации;
- стартовый корпус вопросов пишу я;
- каталог проекта — `~/projects/interview-trainer`.

## Архитектура

Ключевой принцип, вокруг которого строится всё остальное: **вся логика повторений и проверки
ответов — чистые TypeScript-модули без Angular, сети и DOM**. Они покрываются юнит-тестами на
синтетических данных, а Angular-слой только рисует их результат. Ровно тот же приём, что уже
используется в `border-queue-bot` (`bot/events.py` — чистый модуль без IO).

```
src/app/
  domain/            # чистый TS, ноль зависимостей от Angular
    models.ts        # Card, CodeTask, ReviewState, Grade, Topic
    srs.ts           # SM-2: review(state, grade, now) -> ReviewState
    session.ts       # выбор очереди карточек на сессию (due + новые, лимиты)
    verdict.ts       # сравнение фактического вывода кода с ожидаемым
    stats.ts         # агрегаты: по темам, серия дней, доля «знаю»
  core/
    storage/         # IndexedDB через idb: ProgressStore за интерфейсом
    content/         # ContentService: загрузка JSON-корпуса из assets
  features/
    decks/           # выбор темы/колоды, сколько карточек к повторению
    review/          # экран карточки: вопрос -> ответ -> самооценка
    code/            # песочница: Monaco + запуск в Web Worker
    stats/           # прогресс и слабые темы
  shared/            # markdown-рендер, material-обвязка, ui-примитивы
public/content/      # js.json, ts.json, angular.json, code-tasks.json
```

Состояние — **signals** в сервисах (`ReviewSessionStore`, `ProgressStore`), без NgRx: на этом
объёме он был бы карго-культом, а рассказать про signals на собеседовании ценнее.
Роутинг — `loadComponent` на каждую feature, чтобы lazy-loading был настоящим, а не на словах.

### Ядро SRS (`domain/srs.ts`)

Классический SM-2: состояние `{ ease, intervalDays, repetitions, dueAt, lapses }`, оценка
`Grade = 'again' | 'hard' | 'good' | 'easy'`. Функция `review(state, grade, now)` возвращает
новое состояние — чистая, детерминированная, без `Date.now()` внутри (время всегда параметром,
иначе не протестировать).

Инварианты, которые надо зафиксировать тестами сразу, иначе они тихо сломаются:
- `again` сбрасывает интервал и увеличивает `lapses`, но **не обнуляет `ease` в пол** —
  минимум 1.3, иначе одна забытая карточка навсегда застревает в ежедневном показе;
- новые карточки не сваливаются в один день: лимит новых на сессию (`session.ts`);
- `dueAt` всегда считается от момента ответа, а не от прошлого `dueAt` — иначе после недели
  перерыва вся колода «просрочена в прошлое» и порядок теряет смысл;
- время хранится в UTC-миллисекундах, «сегодня» вычисляется в локальной зоне один раз на входе.

### Песочница кода

Запуск — в **Web Worker** с жёстким таймаутом (~2 с) и `terminate()` по его истечении: бесконечный
цикл в задаче не должен вешать вкладку. Внутри воркера подменяется `console` — вызовы собираются
в массив строк, он и сравнивается с ожидаемым выводом (`domain/verdict.ts`, чистая функция:
нормализация пробелов, сравнение построчно, показ первого расхождения).

TypeScript-задачи транспилируются тем же воркером через `ts.transpileModule` (пакет `typescript`
уже в зависимостях Angular) — без проверки типов, только стирание. Проверка типов в задачах
формата «что выведет» не нужна, а тянуть полноценный language service в воркер — лишнее.

Редактор — `monaco-editor` в собственной тонкой standalone-обёртке (`shared/monaco-editor`),
без сторонних Angular-биндингов: они регулярно отстают от мажорных версий Angular, а обёртка
здесь — это `ngOnInit` + `dispose()` + `ControlValueAccessor`. Настройка `MonacoEnvironment`
для воркеров редактора делается один раз в `main.ts`.

### Хранение

`ProgressStore` за интерфейсом, реализация — IndexedDB (`idb`, ~1 КБ). Хранилища: `progress`
(состояние SRS по каждой карточке), `attempts` (история попыток по кодовым задачам), `settings`.
Интерфейс отделён от реализации не ради абстракции как таковой, а чтобы юнит-тесты домена
работали на in-memory реализации и чтобы синхронизацию с бэкендом можно было добавить потом,
не переписывая features.

Корпус вопросов — **статические JSON в `public/content/`**, не в IndexedDB: контент версионируется
в git и обновляется деплоем, а в браузере живёт только прогресс. Связь по стабильным `id`
(`js-eventloop-microtask-order`), поэтому переформулировка вопроса не сбрасывает прогресс.

## Контент стартового набора

Пишу вместе с кодом, в тех же JSON. Ориентир — 120–140 карточек и ~25 кодовых задач:

- **JavaScript (~50):** event loop и микротаски, замыкания, `this` и потеря контекста, прототипы,
  `==` vs `===` и приведение типов, `var/let/const` и TDZ, промисы (`all/allSettled/race/any`),
  async/await и порядок выполнения, генераторы, `Map/Set/WeakMap`, копирование объектов,
  деструктуризация, модули ESM vs CJS, debounce/throttle, обработка ошибок.
- **TypeScript (~40):** структурная типизация, `unknown` vs `any` vs `never`, union/intersection,
  сужение типов и type guards, дженерики и `extends`, условные типы, `infer`, mapped types,
  утилитные типы (`Partial/Pick/Omit/Record/ReturnType`), `readonly`, енамы и почему `const enum`
  спорен, декларации, `strict`-флаги и что каждый включает, вариантность, перегрузки.
- **Angular (~45):** standalone-компоненты, signals и `computed/effect`, change detection и
  `OnPush`, зачем нужен `zone.js` и что меняет zoneless, DI и иерархия инжекторов, `inject()`,
  провайдеры и токены, жизненный цикл, `@Input`/`@Output` и signal-based `input()`/`output()`,
  роутинг, guards, resolvers, lazy-loading, Reactive vs Template-driven forms, RxJS-операторы
  (`switchMap` vs `mergeMap` vs `concatMap` vs `exhaustMap`), интерсепторы, контент-проекция,
  директивы, пайпы и `pure`, SSR/гидратация в общих чертах.
- **Кодовые задачи (~25):** порядок вывода `setTimeout`/промисов, `this` в стрелках и методах,
  замыкание в цикле, всплытие, приведение типов в неожиданных местах, `Promise.all` с ошибкой,
  дженерик-функция с `extends`, сужение union, `switchMap` против гонки запросов.

Каждая карточка — вопрос, короткий ответ и развёрнутое пояснение в Markdown; у каждой кодовой
задачи — стартовый код, ожидаемый вывод и разбор, который открывается после ответа.

## Порядок работы

1. **Каркас.** `ng new interview-trainer --style=scss --ssr=false`, strict-режим, Angular Material,
   базовый layout с боковой навигацией, тёмная/светлая тема, роуты-заглушки на `loadComponent`.
2. **Домен + тесты.** `domain/*.ts` целиком и юнит-тесты к ним (SM-2, отбор сессии, сравнение
   вывода). Пишется до UI — это единственная часть, где ошибка тихая.
3. **Хранилище.** `ProgressStore` (интерфейс + IndexedDB + in-memory для тестов), `ContentService`.
4. **Режим карточек.** Экран колод, экран повторения, самооценка на четыре кнопки, горячие клавиши
   (пробел — показать ответ, 1–4 — оценка), Markdown-рендер с подсветкой кода.
5. **Песочница.** Обёртка Monaco, runner-воркер с таймаутом, экран задачи, разбор после ответа,
   запись попыток в `attempts`.
6. **Статистика.** Прогресс по темам, серия дней, список слабых мест — вход в целевое повторение.
7. **Контент.** Полный стартовый корпус в `public/content/*.json`.
8. **Деплой.** GitHub Actions → GitHub Pages, `ng build --base-href /interview-trainer/`.
9. `README.md` и `docs/PLAN.md` (копия этого плана в репозитории; копия из `~/.claude/plans/`
   после этого удаляется).

## Ключевые файлы

Проект создаётся с нуля, поэтому «изменяемых» файлов нет; критичные для замысла — эти:

- `src/app/domain/srs.ts` и `src/app/domain/srs.spec.ts` — ядро повторений и его тесты;
- `src/app/domain/session.ts` — сколько карточек и в каком порядке показывать;
- `src/app/domain/verdict.ts` — сравнение вывода кода, без DOM;
- `src/app/core/storage/progress.store.ts` — интерфейс + IndexedDB-реализация;
- `src/app/features/code/runner.worker.ts` — исполнение кода с таймаутом и подменой `console`;
- `src/app/shared/monaco-editor/` — обёртка редактора;
- `public/content/*.json` — корпус вопросов и задач.

## Проверка

```bash
cd ~/projects/interview-trainer
npm test                 # юнит-тесты домена: SM-2, отбор сессии, сравнение вывода
npx ng build             # сборка проходит в strict-режиме
npx ng serve             # ручной прогон
```

Ручной сценарий, который нужно пройти целиком перед тем, как считать этап готовым:

1. Открыть приложение — на экране колод видно число карточек к повторению по каждой теме.
2. Пройти сессию из нескольких карточек, поставив разные оценки; убедиться, что `again`-карточка
   возвращается в этой же сессии, а `easy` — нет.
3. Перезагрузить страницу — прогресс сохранился, счётчики к повторению уменьшились.
4. В песочнице решить задачу с правильным и с неправильным ответом; проверить, что показывается
   расхождение вывода и что разбор открывается только после ответа.
5. Запустить задачу с бесконечным циклом (`while(true){}` вписать руками) — вкладка не виснет,
   через ~2 секунды приходит сообщение о таймауте.
6. На экране статистики видны пройденные карточки и слабые темы.
